C'est le rite de passage absolu du projet Minishell ! Ce que tu observes n'a rien à voir avec ton parseur ni avec les signaux. C'est un problème fondamental de gestion des File Descriptors (FD) dans la partie exécution de ton binôme.

Ton programme ne plante pas, il fait exactement ce qu'on lui demande : il attend éternellement. Voici le vocabulaire et la mécanique système pour comprendre pourquoi les cat refusent de se terminer.
1. Le Vocabulaire des Pipes

    Vocabulaire - File Descriptor (FD) : Un numéro qui représente un fichier ou un flux ouvert. Chaque pipe créé avec la fonction pipe() génère deux FDs : un pour lire (le bout de lecture) et un pour écrire (le bout d'écriture).

    Vocabulaire - End Of File (EOF) : C'est le signal "Fin de fichier". Un programme qui lit des données (comme cat) s'arrête automatiquement lorsqu'il reçoit un EOF.

    La règle d'or du Pipe : Un pipe n'envoie un EOF à son lecteur que si et seulement si TOUS les bouts d'écriture de ce pipe sont fermés dans absolument tous les processus existants (le parent et tous les enfants).

2. La Mécanique du blocage (Pourquoi ça freeze ?)

Prenons ta commande cat | ls.

    L'exécuteur crée un pipe.

    Il fait un fork pour cat. Ce cat lit sur le pipe.

    Il fait un fork pour ls. Ce ls écrit (théoriquement) sur le pipe (même s'il s'en fiche et écrit sur le terminal, le pipe est là).

    cat commence à lire. Il a besoin d'un EOF pour s'arrêter et rendre la main.

Le problème : Quand l'exécuteur (le Minishell principal) a fait son pipe(), il a ouvert un FD d'écriture et un FD de lecture pour lui-même. S'il oublie de faire un close() sur ce bout d'écriture dans son propre code (le processus parent), alors le bout d'écriture reste ouvert.
Puisque le parent possède toujours un moyen d'écrire dans le pipe, le système d'exploitation se dit : "Attends, le parent va peut-être envoyer du texte plus tard". Donc, il n'envoie pas de EOF. Donc, cat attend éternellement.

Dans ton cas (cat | cat | cat | ls), tu as 3 cat qui attendent chacun qu'on ferme le bout d'écriture de leur pipe respectif.
3. La Solution Architecturale (Pour l'Exécuteur)

Ton binôme doit être d'une rigueur absolue avec la fonction close(). Pour que la chaîne ne bloque jamais, il doit appliquer ces deux règles :

Règle A : La propreté des Enfants
Lorsqu'un processus enfant est créé, il hérite d'une copie de tous les FDs ouverts par le parent.
Avant de faire execve, l'enfant doit fermer tous les bouts de pipes dont il ne se sert pas. Par exemple, si l'enfant 2 lit sur le "Pipe A" et écrit sur le "Pipe B", il doit impérativement faire un close() sur le bout d'écriture du "Pipe A" et sur le bout de lecture du "Pipe B", ainsi que sur tous les autres pipes existants.

Règle B : La propreté du Parent (La plus importante)
La boucle principale de l'exécuteur (celle qui fait les fork) doit impérativement faire un close() sur les deux bouts d'un pipe dès qu'elle n'en a plus besoin pour brancher un nouvel enfant.
Si le parent garde un seul bout d'écriture ouvert par oubli, toute la chaîne restera paralysée.
